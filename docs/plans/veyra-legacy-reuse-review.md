# Critical review: original Veyra versus current Ingenium

Reviewed source intent: F01–F68/H01–H06 (74 entries), the original Windows specification, existing Windows source and current Ingenium route/control inventory. This is a recommendation and source inventory, not a new runtime certification.

## What to reuse first

The original Veyra is more than a mockup: Rust/Tauri shell, a service/core/adapters/contracts split, generated TypeScript contracts, navigation and appearance components, native browser work, interactive terminals, WSL workspace access, selected-user configuration and command journaling, attachments and recovery/review panels exist in source. Native Windows + explicit WSL identity are the most valuable capabilities that current Linux-focused Ingenium does not provide as a desktop application.

Evidence entry points in the Windows repository: apps/desktop/src-tauri, apps/service, apps/web, crates/contracts, crates/core, crates/adapters/src/wsl_workspace.rs, crates/adapters/src/wsl_command_journal.rs, apps/web/src/features/terminal/InteractiveTerminal.tsx, apps/web/src/features/workbench/followUpQueue.ts, apps/web/src/features/workbench/WorktreesPanel.tsx and apps/desktop/src-tauri/src/native_browser.rs.

The latest stopped development checkpoint is fb608696f0cc4578ba877aa262c61b79d6beaafe. Its README describes v0.3.0-preview.1 as a published Windows coding preview, with newer browser/goals/attachments/ConPTY/editor integration not in that artifact. The implementation ledger explicitly retains native/whole-service/WSL acceptance gates. Therefore source reuse is warranted; saying every WSL/runtime feature already works would be unjustified.

## Where Ingenium is better

Ingenium already has the application breadth: real mail/OAuth/sync, Docs/RAG/history, structured Tasks, observations/personality/context, proposal-based skill synthesis and persistent storage, organizations, encrypted secrets, jobs/event queue, backups, usage/logs/status and deployed cluster boundaries. Keep those systems rather than transplanting a less complete Windows alternative. Its API-owned SQLite/migration/capability model is worth retaining during Rust work.

## Where current Ingenium needs criticism

The current navigation is an administrative feature directory with weak workspace/environment orientation. Important actions can be buried across settings and feature pages; duplicate entry points risk inconsistent forms. Step-up errors can strand users; valid uploads can be misreported as invalid files when the actual failure is authentication/network/API. Embedded editors require coherent auth/reconnect/recovery. README tool/view counters have drifted from current inventories. Healthy processes/page responses have too often been easier to prove than fresh chat, full synthesis, mail or persisted user workflows. A new theme alone fixes none of those issues.

Adopt clearer native/WSL/cluster scope, search/keyboard navigation, recoverable pending operations, source/provenance and honest capability/error states. Keep the feature depth.

## What not to carry forward automatically

Do not resume the custom inference-engine program, turn Linux into a model host, duplicate OpenCode Web's frontend, build a competing scheduler/memory store, or revive custom multi-chat orchestration. Broad maps/sites/pets/fully collaborative/mobile/cloud parity is not automatically more valuable than a stable workspace. Those original rows remain visible with recommended deferrals, requiring explicit disposition; they are not erased or declared complete.

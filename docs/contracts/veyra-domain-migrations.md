# Veyra domain migration allocation

The coordinator allocates122 (projects/installation aliases),123 (learned memory) and124 (Dot) on the existing API database connection. These add metadata only; no existing project, transcript, resource, secret, preference or encrypted bytes are moved, removed or rewritten. The original resource owners and credentials remain authoritative.

The allocated SQL derives from each domain's reviewed proposal and adds organization/user foreign keys. Memory uses generated organization/owner references from its canonical six-axis scope key, retaining the existing positional insert contract. Project/native identity and execution admission are checked by the authoritative adapters; an installation alias is never permission to execute. Projectless remains private.

The core migration owner applies each domain atomically, refuses partial schemas, checks foreign keys and verifies immutable memory receipt/suppression/watermark triggers on reopen. A migration does not enable a route, inference, extraction, scheduler or Rust writer. Original tables/IDs survive rollback to the old presentation; never restore a database file over a running writer.

Production copy, original-row hashes, ACL/resource identity, restart/restore and exact deployment qualification remain required before release. No production migration has been executed at this source checkpoint. Writable Rust cutover retains its separate recorded approval gate.

Migration122 also creates one opaque persisted installation identity. API-owned catalog/alias rows reference it. It is independent of any global project name, account or workspace; archive/restore preserves it. Cloning to a different host requires explicit host identity handling and never authorizes memory sharing. Installation resource mapping remains an explicit reviewed alias import, not automatic folder discovery.

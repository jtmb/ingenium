# Workspace successor executions

Coordinator allocation138 extends workspace executions137 on the same Core connection. Legacy project runtimes retain one runtime per workspace. Workspace executions retain every original runtime, immutable provisioning receipt, context/source mapping and credential receipt. A new execution has a new runtime ID and backend name; it never replaces the original provisioning receipt or adopts an old container.

A private workspace has one selected execution head. A successor requires a terminal predecessor plus a fresh authenticated original-manager stop observation bound to the retained daemon, parent container, original start and profile. Merely setting STOPPED, observing a missing container, changing a lease or presenting caller metadata cannot grant restart. Stop withdraws live credentials, browser access and connections before the manager acts; uncertain stop remains unavailable and is reconciled by the same owner. No user data, source directory, old runtime row or container is deleted.

Migration138 is lossless and validates the exact137 predecessor receipt and original immutable recipe before and after evolution. Source136/137 recipes stay unchanged. The selected head is seeded from the sole existing execution without fabricating retirement. Database constraints retain legacy uniqueness and deny overlapping/unretired workspace successors. New executions require fresh image approval, fresh credentials and original provisioning/bootstrap. Saved history remains readable through its existing human authorization. Physical stop/restart, engine use, persistence and cross-generation memory remain separate release acceptance.

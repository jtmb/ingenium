# Installation-owned archive retention

General settings reads and writes archive retention through `/api/v1/installation/preferences/archive-retention`, without discovering or selecting a workspace/project. This is the first migrated installation preference; the complete legacy project and installation-settings replacement remains open.

The existing Core database and settings writer remain authoritative. Original bootstrap binds the one verified canonical legacy storage ID to the existing migration122 installation reference. This only records metadata. Existing settings, credentials, encryption, paths, models, workspace ownership and IDs are preserved. Ambiguous canonical storage or a conflicting prior reference refuses adoption. An established reference is not overwritten or reassigned from browser input. No production database was migrated during this source qualification.

The router follows the original authentication, rate and CSRF middleware. Its request owner revalidates the current human browser session and original installation-admin permission on every operation and again inside the original transaction. Compatibility credentials, service credentials, organization-admin status alone, a selected-project query and extra body fields cannot select or grant installation access. Only archive retention is exposed by this endpoint; credential/provider keys remain in their original protected owners.

The GET returns the exact stored value (including absence) plus the installation reference revision and a hash of the original storage identity, key, revision and exact value. The PUT requires an explicit UUID operation, the same revision/hash and a canonical integer string from1 through365. It calls the original settings writer, verifies readback, advances the reference revision and records the operation in the existing Core operation ledger in one transaction. A failed write or lost permission rolls everything back. The exact hash detects changes through retained compatibility routes even when they did not advance the reference revision. Revision exhaustion refuses before writing.

An identical operation replay performs no second write and returns the current setting with the original applied revision. Reusing its ID for another request is a conflict. The panel disables duplicate writes, withdraws old state on account/session/status changes and ignores late replies. On an unknown response it offers a fresh read of the actual setting, without automatically repeating the write. It neither supplies an invented saved default nor normalizes an invalid legacy value without an explicit edit.

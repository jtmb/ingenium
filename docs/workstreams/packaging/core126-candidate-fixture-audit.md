# Candidate qualification bootstrap audit

Source audit only, 2026-10-30. Root requested an architectural audit while it continues original image/Native wiring. No Docker, model, engine, dependency, build, SDK, runtime, database, HTTP or shared-source operation was performed. Current source inputs and hashes are in core126-candidate-fixture-audit-inputs.json. This is a proposal for Root's decision, not an installed API or qualification witness.

**Finding: no existing public-canary fixture factory can currently produce the unapproved managed attempt needed by openOriginalCase.** Ordinary provisioning can establish a real original candidate parent without image approval. The existing Core can create a real authorized public-canary Job and Dot-claimed JobRun without starting a process. But the only existing managed-attempt/credential/bootstrap path requires independent image approval first. Changing a supplied flag, calling another existing route or recording a synthetic profile does not break that cycle legitimately.

## Reusable existing owners and exact sequence

1. Use a dedicated public-canary-only authorized workspace/project and the existing caller's actual project permissions. Never copy customer storage, DB, source messages or credentials. Core `runtimes.authorizeWorkspace({id, organizationId, projectId, ownerUserId, storagePath})` (runtimes.ts220) writes an original authorized workspace in execTransaction and checkpoints. An existing authorized public-canary workspace may be reused only with its genuine scope/current epochs. A direct Core function is not an authorization grant; Root must retain the real request/owner authorization checks.
2. Existing runtime-provisioner.ts `ensureRuntime(workspaceId)` calls its original provision flow. It uses `runtimes.createRuntimeInstance`, original runtime capability owner, original state/lease CAS and `provisionManagedRuntime` through the existing authenticated manager. The manager uses buildRuntimeContainerSpec, existing workspace mapping/private network, GET daemon/image, immutable image create, real start/attach and final inspect. New-flow `originalProvisionFromNewFlow` is retained by the authenticated client and committed in `transitionRuntime(... STARTING, originalProvision: authenticatedOriginalProvision(managed))`. This establishes birth/provenance, **not image approval**. Actual manager/reconciler health is still required for READY/IDLE; never call recordRuntimeHealth/transition merely to assert success. Existing-reused/legacy-unqualified responses do not manufacture a birth receipt.
3. Existing `agents.createAgent(projectId, 'qualification', publicFixedSystem, ..., permissions)` and `getJobAgentConfig(projectId,'qualification')` can provide the real five-field projection. createAgent writes the normal agent profile as well as its Core transaction, so it belongs only in the explicitly owned public-canary scope. Preserve default-deny and exact original JSON hash. Never create the reserved broker through this public function.
4. Existing `jobs.createJob(projectId,name,description,'qualification',fixedCanaryPrompt,undefined,null,boundedTimeout,[],ownership)` commits the real Job through execTransaction/checkpoint. Ownership and original principal/grant remain genuine. If no servicePrincipalId is supplied, ensureAutomationPrincipal creates/reuses Automation Dispatcher and inserts a project execute grant; this is a real side effect, not a read-only fixture shortcut. Root should use an already authorized public-canary principal/grant when available, or explicitly account for the normal narrowly scoped owner-created grant. No broader credential/grant or customer project is a substitute.
5. The usable **no-process claim** is the existing `createCoreRequestDotSession(realAuthenticatedRequest, selectedScope, originalRunner, options).service`: `propose` (or idempotent proposeForSource), `approve` with a real one-shot schedule, then `service.reconcile` when due. The original request-session adapters revalidate the real request. Dot authorization/source/capability checks remain active. In core-binding.ts, `jobs.claim` calls existing `jobs.startJobRun(projectId,jobId,'cron',{scheduledFor,expectedScheduleRevision})` inside the same Core/Dot transaction. DotService.reconcile persists the matching claimed operation before returning. It does not start a process. Do not call runtime.dispatchJob, which proceeds to execution.
6. Step5 is conditional on a **genuine existing source producer**, not arbitrary source JSON. request-binding.ts requires a real canonical source chat/message or trusted maintenance event/memory. A user source must match the actual message hash, authorized canonical chat/session and sourceRuntimeId/sourceSessionId metadata. Root may use a newly produced public fixed-canary source through the real source owner; manually appending metadata that claims opencode-chat provenance or seeding a claimed operation is not equivalent. No source fixture authority/factory bypass was found in this audit.
7. The claimed JobRun retains original revisions, automation grant, principal, membership, quota, parent/runtime/workspace and Dot-operation checks. It can reach `factsForImagePreparation`, but **cannot currently reach managed prepare** for an unapproved candidate. There is no supported method here to issue its managed attempt or private job-run credential early.

Do not use HTTP jobs/:id/run: it calls jobs.startJobRun then immediately fires executeJobRun. Direct `startJobRun(...,'manual')` also does not create the matching Dot operation, and stores schedule_revision=NULL whereas current core126.base requires equality with the numeric Job schedule_revision. Even direct cron claim alone lacks the original Dot operation. Neither is an openOriginalCase implementation. Ordinary runtime credentials have audience runtime and broader generic runtime scopes; never substitute them for a job-run credential or relax job-run audience checks.

## Smallest viable same-owner extension (not implemented)

Root needs an explicit **inert qualification purpose** in the original Core admission/credential/bootstrap owner, backed by the same original database, transaction/CAS fences, manager, runtime birth/proof and private control owner. This is a new execution primitive; it cannot be implemented by populating currently approved-profile fields with placeholders.

- Introduce a discriminated original admission purpose such as production versus candidate-inert. A candidate intent binds the real public-canary run/attempt, original physical parent/container start/profile, image/source/static/schema/probe hashes, exact case/nonce, fixed original agent/model trap/catalog hash, current existing grants/epochs/quotas and a short absolute deadline. Original Core must issue and consume it once. It conveys narrowly bounded inert execution authority, never production image approval. It must not be accepted by normal prepare/current/assertAdmissionOriginalImage or a normal job launch.
- Keep original Core as the single writer. Reuse its original run and existing effect-intent/create/start/retirement ordering. Represent unapproved candidate evidence separately and honestly: production profile columns are currently required/immutable, so Root must design the necessary schema/discriminator change rather than invent a profile ID/hash, approvedScopes or qualified/profileQualified:true. Rechecks before/inside Core transactions must retain all base identity, original source, current grants, membership, epochs, deadlines and quotas. No SQL transaction may span Docker/native async work.
- Extend the **existing** job-run credential issuer/inspector and original HTTP/assignment/private bootstrap path to bind this purpose and case. The credential remains original run/attempt specific, with only the fixed public-canary tool/project and qualification control operations. Parent runtime credentials, admin/service bypasses, caller-selected scopes, another credential authority and a second DB are excluded. Every normal assignment/MCP/result route must reject candidate-purpose use outside that exact lease. A missing lease, case mismatch, lost control owner or revoked grant must fail before model/tool/spawn effects.
- Let the same original manager/container/child launch code consume the explicit candidate-purpose private frame. Keep actual executable/argv/agent/material/current assignment checks shared and observed. The candidate branch may invoke only the source-pinned inert harness with the fixed intercept and closed network/config; no arbitrary command/prompt/provider/permission/environment override. Changing image bytes, using an uninstrumented mock child or qualifying a different SDK/launch branch cannot prove the production path. Record actual authenticated spawn, route, native hook/fallback and result-journal effects from those same owners.
- Original withdrawal revokes this exact case first, and original manager wait/inspect positively joins all retained children/container before final result consumption. Lost acknowledgement remains unknown, not retry/reissue. Qualification records cannot be promoted into production attempts. Only all eighteen actual case results on the same immutable closure, then independent protected approval, can enable a **fresh** normal managed admission. In particular the unqualified-assignment-denial case must still show that an ordinary unapproved assignment cannot launch; a narrow qualification lease cannot silently become a global exemption.

Until Root implements and reviews that primitive (or supplies an already existing equivalent not found here), openOriginalCase must return INCOMPLETE. No fixture produced by existing API calls alone can honestly provide all current fields. This report supplies grounded reuse points and the missing boundary; it does not claim that naming an interface supplies authority.

## Frozen integration contract after Root's architecture decision

Root accepted candidate-inert purpose in the same original Core/manager owner. The identifiers below are proposed additions, not names of already installed methods. Existing production behavior is the default. Worker provides `tools/veyra-release/core126-candidate-intent.mjs` plus declarations and nine dependency-free CPU tests. The utility validates a closed public-data intent and compares hashes; it **does not issue or validate the provenance of an original lease**, approve an image, provide a principal or create a credential. It rejects extra fields (including approval/profile/credential/command/trace/brand), non-JSON descriptors, arbitrary cases/models/tools/trap URLs, NULL schedule revision, changed scope/revisions/hashes and expired/overlong intent. Maximum candidate lifetime is120000ms; original Core must additionally cap it by the actual parent/control/grant deadlines. The Core agent definition hash and image/source/artifact hashes still come from the original owners, never this helper. Feed only bounded strict-parsed JSON (reuse original parseStrictJobJson); the DTO helper cannot recover duplicate keys discarded by another parser.

Proposed data/authority split:

```ts
type AdmissionPurpose = 'production' | 'candidate-inert-v1';
// Runtime identity lives only inside the actual Core owner WeakMap/ALS.
// Do not export a constructor or accept JSON containing this brand.
declare const originalCandidateLeaseBrand: unique symbol;
type OriginalCandidateLease = Readonly<{[originalCandidateLeaseBrand]: true}>;
type OriginalLaunchAuthority =
  | {purpose:'production'; approvedProfile:OriginalApprovedProfile}
  | {purpose:'candidate-inert-v1'; lease:OriginalCandidateLease;
     intent:CandidateInertIntent; intentHash:string};
```

A TypeScript unique symbol is not the runtime brand. Core's lexical WeakMap must bind its own object identity to the persisted original intent/case/fence/current facts; an object literal, copied DTO/hash, JSON round trip or frozen DTO cannot acquire it. The brand cannot cross the manager/container process boundary. The existing authenticated managed-job Core client and private one-use frame must bind the serialized purpose/intent hash to that server-owned admission; the receiving manager/bootstrap seals its own observation only after the original authenticated exchange/current assignment checks. No alternate client/token or portable authority token is introduced. The candidate intent may last at most120s, but each effect/assignment still needs its own actual fresh manager observation (existing proof expires after5s), ALS-scoped continuation and rechecked original facts; the longer intent must not stretch the short observation lease.

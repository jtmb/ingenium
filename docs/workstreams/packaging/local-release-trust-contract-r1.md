## Private record and field semantics

Fixed proposed location: <native-derived InstallRoot>/private-web/local-release-trust.json. It is not inside versions/<release>-<manifestSHA> and not copied from the candidate package. Its fixed path is derived from the running native installation; no browser/renderer path, URL, PID, hash, publisher, policy flag or environment override selects it. Parent directories/leaves must be plain local files under the established root. The original writer alone creates/replaces it; browser clients have no file/write/issuance operation. This is a local custody boundary, not a cryptographic signature on the JSON.

local-release-trust-field-schema-r1.json is a closed version1 field proposal, maximum64KiB raw UTF-8. Reject duplicate keys at every depth, unknown fields, wrong types, unsupported version, NUL, excessive nesting, noncanonical hashes, malformed UTC, unsafe/root-escaping paths and non-local/reparse/hardlinked/delete-pending files. The schema alone does not implement these semantic/file rules.

- issuer identifies the original reviewed release/install operation and timestamp for provenance, not an authenticating magic string.
- release binds reviewed source revision AND source snapshot SHA, actual build-receipt SHA, packaged-artifact/release-receipt SHA, release version, Windows x64 target and MSVC build target. Each digest must identify an actual immutable Root-reviewed receipt with matching content, not an arbitrary well-formed hash. These receipts attest source-to-build provenance; startup byte comparisons do not independently reconstruct a binary from source.
- expected pins the independently supplied MANIFEST.json SHA and separate Desktop/service file names, expected SHA256, length and AMD64 PE machine. The expected executable facts originate in Root's reviewed build/package output receipt; copying the candidate manifest files array into this record is not independent issuance. File hashes observed by the consumer are comparison operands only.
- selection pins the native-derived install root, computed selected version directory, SHA256 of the ORIGINAL writer's exact committed current-install.json bytes, action and prior manifest/selection/trust lineage. The selected directory must equal root/versions/<reviewed-release>-<expected-manifestSHA> and match the exact current row; do not accept arbitrary directories from JSON. The previous fields are history, never permission to activate or trust the previous payload. Initial install has null prior fields. A previous installation with no independently reviewed trust can be recorded as history but cannot become rollback authority. Update/rollback/review-existing requires Root to validate and capture applicable originals; a rollback needs its own independent approved artifact receipt and fresh selection binding. No fallback to an old matching manifest while current selection differs.
- publisher_policy is exactly one mode. verified_expected_publisher requires an independently approved expected certificate SHA1 thumbprint plus the existing Windows cache-only/no-revocation Authenticode policy to succeed against both retained executable handles. Source signature.rs:71–136 requires successful provider policy and actual signer comparison; its DTO explicitly says publisher_trust not_independently_approved. The private native verifier must derive success from the retained operation/result, not accept a projected signature JSON supplied by a client. Preserve any existing four-executable installer/signing checks.
- locally_reviewed_exact_build requires the SAME reviewed packaged-artifact receipt SHA as release and exact independent manifest, source, build, architecture and executable facts. signing_claim is none. It means local review of exact bytes; it does not mean unsigned is signed, a publisher was verified, revocation was checked, or feature acceptance passed. No automatic downgrade from a failed/unknown signed-publisher check. Root must choose this policy explicitly for the particular completed build; no runtime/provider fallback.

## Original writer procedure and failure behavior

1. Root completes and reviews the exact source/build and packaged output using the existing release flow. Capture independent manifest and Desktop/service output hashes/lengths/PE machine in a minimal immutable release receipt. Validate original receipt provenance and policy explicitly; the staging manifest or candidate inspector cannot serve as that approval. No receipt exists merely because a template has hash-shaped fields.
2. Within the existing explicit local installer operation, preserve the previous selection/trust original and call the existing Read-VeyraPackage/Select-VeyraInstallation flow. Existing quiescence is required; never stop processes to obtain it. No new runtime lifecycle approval is implied.
3. A new NON-EXPORTED private module helper receives the original Root-reviewed release context through Root's trusted local release driver, not through a browser command/HTTP endpoint/IPC request, package DTO, ambient environment, generic file picker or public module export. It has no default authority and cannot construct expected facts from $Package.Manifest or inspection output. Calls without original context follow normal install behavior and leave private Web unavailable when no valid matching sidecar exists. Root must wire this context from its actual reviewed-receipt producer; until then the hook is inert/gated.
4. At the193 success boundary, read back the exact original writer selection under native file custody, compare it and installed files to the independent context, and bind its final byte hash/lineage. Revalidate all source/payload/receipt identities through the write. On the155 early return, issuance requires a separate explicit Root review of this exact selection; ordinary repeated install must not mint, refresh or repair trust.
5. Write a bounded UTF-8 sidecar to a new same-parent file, flush, read/hash/check its handle, and publish only if the previously captured sidecar/absence and selection remain exact originals. Preserve an existing record and unique failure evidence on unknown/failed publication; never overwrite a changed original, delete a refused target or retry through an alias. Root supplies the actual bounded Windows file-custody writer, rather than assume existing Write-VeyraState is sufficient against replacement races.
6. Selection and trust publication are NOT an atomic two-file transaction. If selection succeeded but record publication/readback failed, report selection success and private-Web trust unavailable separately. Preserve normal features, selected payload, rollback originals and the old/staged minimal record; do not roll back, switch services, stop a process or synthesize a successful record. A stale old record cannot authorize the newly selected pair. Root reconciles unknown originals explicitly.

No existing tool helper inventory expands implicitly. If Root puts the private helper into Veyra.Install.psm1, the reviewed source/package receipts must include that changed existing helper before issuance. No new install-helper file is silently added to strict staged package inventories. No new exported SetTrust/ApproveCandidate operation or writable service route is proposed.

## Retained startup inputs, not an inspection DTO

Add a separate Windows-only private adapter, proposed installed_package/local_release_trust.rs, with a non-serializable RetainedLocalReleaseInputs object. Its factory is callable only by the actual native installation/startup owner from the actual current executable and initialized captured service owner. Its constructor/fields are private; no Deserialize/DTO conversion, generic positive callback, bool-approved constructor or public expected-facts arguments. Root binds the actual owner types during integration. It does not construct a browser authority or start a handshake.

The retained object owns live read handles plus windows_file_metadata::FileIdentity (volume and128-bit id), PhysicalMetadata and observed comparison hashes for the sidecar, current-install original, manifest, Desktop exe, service exe and necessary plain ancestors. Hold relevant immutable original release/build receipt handles if those facts are consumed locally; do not reopen another receipt by a caller path. Reuse Reads-style guards (local fixed drive, OPEN_REPARSE_POINT, file share read only; directory read/write sharing without delete; no reparse/delete-pending/multilink/offline placeholders), but DO NOT return the existing InstallationInspection/CandidateInspection Custody: installed_package.rs:273–318 documents that it closes handles and stores historical identities. RetainedLocalReleaseInputs must keep the actual File objects until the private broker owner explicitly ends them. Confirm PhysicalMetadata on those SAME handles at startup completion and each dependent admission/liveness boundary; no reopen-by-path replacement, token-shaped JSON or current PID substitute.

Compare only against independently issued expected facts: exact manifest bytes/hash/revision/target, actual PE machine and Desktop/service bytes/lengths/hash, selected root/version/current-install bytes/lineage and chosen publisher policy. Existing package inventory validation continues unchanged. The running Desktop and captured initialized service executable must both belong to the same currently selected approved package pair. Existing observe_startup permits reporting previous/target mixed execution; a mixed pair stays private-Web gated. Do not infer loaded-memory identity, remote-client identity, process-birth continuity or a kernel peer merely from on-disk files; Worker1's later process/peer owner and admission contract remain separate.

Proposed factory output is only the retained private package-input dependency for Root's eventual ApprovedPackagePair implementation (BROKER-CONTRACT.md:51–58). It is not the broker capability itself, approval of a window, a discovery secret, a listener, a startup Hello, a peer or a writable public API. No handshake work is included.

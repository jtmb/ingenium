## Smallest genuine owner and sequencing

Replace the entrypoint's first current-Core initialization with a root-owned, fixed startup executable, running its DB work as the same API uid/gid and with the validated old API locator context. It may import builtins and the reviewed capture helper statically, but no current Core/API module. Deployment pins its paths/hashes; it accepts no HTTP body, renderer path, module URL, proof flag or browser authority. Root must package it through the existing trusted entrypoint/Docker/runtime-copy allowlists and source-chain validation, preserving all current filesystem/uid checks.

1. Acquire Root's existing approved exclusive upgrade custody before opening either owner: prior API, extension/runtime/job writers and old plugin/config consumers must be drained/fenced by their actual owners. A SQLite write transaction alone is not cross-process/filesystem deployment custody. This source review does not stop anything or grant disruption authorization.
2. Verify the actual prior deployment/code identity and raw launch contract plus the pinned old runtime closure. Verify the DB is the same intended existing file using the original owner/deployment contract; never create a fallback sibling. Preserve the raw DB env value, including unset/relative spellings. 3. Import the exact old `db.js` and `tools/paths.js` by canonical absolute file URLs without query aliases. Explicitly invoke the original old `getDb()` in that process, then call the reviewed `captureLegacyPluginPaths` helper with the exact old module paths/hashes and a real active non-global project from that owner's own DB. 4. Persist the exact observed capture once in Root's approved private durable location, with original ownership/link checks, atomic durable publication and a trusted pin/upgrade receipt. Pass `INGENIUM_PLUGIN_LEGACY_CAPTURE_FILE` and its exact SHA to the later API via a deliberately extended run-api environment allowlist, reading trusted startup state rather than arbitrary user env. The current positive owner still performs actual browser review/session/CSRF/step-up/project/installation checks and preimage matching before any filesystem transition; startup capture does not grant migration/plugin execution authority.

A same-process dynamic current API import is viable for a standalone launcher that has no earlier current getDb caller: import it only after capture+old close, then explicitly invoke exported `startApiServer()`. Dynamic importing `api-server.js` alone will not start it because its main-module check compares argv[1] to its own URL (443-448). The proved container chain already has a separate DB-init child, so keeping that dedicated original-owned sequential bootstrap is smaller than changing API listener ownership. It also avoids starting the full old API, scheduler, mail or providers just to capture original DB/locator ownership.

## Durable restart rules, not an opportunistic DB probe

Root must own distinct durable states: approved pre133 upgrade not started; capture committed/old closed; current upgrade may have started; current generation acknowledged. On the first upgrade, the deployment's actual prior owner/code and exclusive custody establish pre133 status. Once current initialization may have run, never re-open old Core or re-capture to make a missing witness appear valid. Reuse the immutable capture/pin on restart; current migration failure/partial state retains its original evidence and closes/fails through the current migration owner. A known upgraded instance without a prior capture remains unproven; a late capture cannot repair history.

A genuinely new database can use the existing fresh initialization branch, with newness proved by that same entrypoint's exact successful exclusive file-creation ownership. Do not add an operator `fresh=true` override for an existing DB. Existing installations with no active non-global project are an explicit helper limitation: it currently requires a real active project selector. An original-owned empty-cohort observation branch may be designed for a genuinely empty installation; archived/ambiguous claims must not be skipped or a fake project synthesized. No such branch was implemented or qualified by this review.

Capture time alone does not fence configuration/source files or all consumers. Retain legacy raw originals, the old runtime, minimal code/launch/capture receipts and actual fail witnesses until their remaining consumers/rollback requirements close. Give the packaged prior runtime a concrete end condition: last authorized pre133 capture/upgrade plus Root's explicit rollback consumer closure, not an indefinite duplicate evidence build. Existing golden consumer remains protected now.

## When a prior compatibility deployment is needed

If Root cannot supply the actual prior runtime/launch identity or cannot package the pinned old owner closure in the new upgrade artifact, use a prior compatibility release of the actual pre133 owner with a normal explicit capture startup/shutdown hook and no133 code/import/migration. It must preserve the deployed plugin resolver behavior and run in the actual service context, capture under real maintenance custody and publish its original handoff before the subsequent133 release. This needs a real compatibility build/deployment and acceptance, not an inspector, REPL injection, dynamic patch of an old running process, copied SQLite handle, restored historical guess or changed golden dist. The old compatibility release can itself perform ordinary pre133 startup work; preservation needs qualification.

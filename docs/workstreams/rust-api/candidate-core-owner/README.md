# Candidate purpose: bounded Core owner proposal

This source proposal implements explicit persisted-purpose refusal at the existing Core126 owner, credential inspector, authenticated wrapper and normal HTTP/tool boundary. It does **not** implement a genuine candidate lease constructor or enable candidate effects. That constructor remains Root-owned. The seven canonical targets and exact pre/post hashes are in `preimages.json`; Root alone applies the patch, registers SQL129 and reviews the resulting integration. Shared files, existing data and encrypted credential bytes were not written here.

The frozen architecture is the packaging candidate bootstrap audit and its source/hash map. The Root draft SQL129 was read as input; it was neither changed nor registered. Tests apply actual SQL126 and draft SQL129 only to an in-memory SQLite database. Activation of this source requires SQL129 installed through the original Core migration transaction first. Missing persisted purpose fails closed; there is no pre-migration caller/DTO fallback. SQL-only preservation tests or these fixtures do not qualify migration deployment or candidate runtime acceptance.

## Implemented boundary

- The original Core row supplies `purpose`, never headers, selection DTOs, admission JSON or an optional flag. `describeStoredManagedPurpose` distinguishes production from candidate-inert-v1. It requires real production profile fields and null candidate columns for production. The production `admission_json` and existing specHash algorithm remain unchanged. All base permission, genuine Dot operation, run/source, revisions, grants, principal/member/parent/epoch/quota and profile checks remain the existing code.
- Candidate purpose requires null production profile fields, strict bounded duplicate-key-refusing JSON, the closed pure intent schema and matching intent digest, plus exact persisted run/attempt/source identity, scope, revisions, parent/image/resource/deadline columns. This validates data identity only. It cannot manufacture provenance or a lexical brand. An expired intent remains inspectable as data; that does not permit an effect.
- The private owner `admissionPurpose` exposes only the stored purpose/hash descriptor. Normal owner `read/current/prepare/launchMaterial`, assignment and bootstrap paths refuse a candidate before an image/profile/provider/material/credential effect. The private `prepareCandidateInert` accepts only the existing four-field original selection, performs existing base checks, then returns the explicit unavailable error. It accepts no DTO/hash/lease/callback that could act as positive authority and creates no row, credential, Run, grant or quota claim.
- The original credential binding joins are preserved. Candidate issuance/inspection stays closed. Production issuance uses the existing token/encryption owner and SQL129 defaults; inspection now also matches immutable persisted production purpose and null candidate hash. Its returned credential explicitly records that production purpose. No token is rotated, copied or re-encrypted. Normal assignment, bootstrap, HTTP and tool wrappers require that discriminator. Withdrawal remains the existing exact self-reduction path and is not promoted into execution authority.
- Authenticated internal wrappers discriminate the stored original before the production image continuation. Runtime wrappers discriminate the original credential and stored admission. Unknown purpose and candidate use never fall through to the approved-profile branch. There is no caller purpose header or generic positive candidate port.
- The original material-admitted CAS still commits before await or credential work. The patch changes none of the existing create/start/unknown/retirement fences or journal writes. A lost async/material acknowledgement cannot issue replacement material, rotate credentials or reset unknown effect state.

`OriginalCandidateLease` in the declaration is a nonconstructible documentation type, not a runtime implementation or a portable authority. No function in this proposal returns it. Existing production admission/material/assignment types remain production types; no union is cast into them and no `profileQualified:true`, profile ID/hash, approved scopes or model binding is invented for candidate.
